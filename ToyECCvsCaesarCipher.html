1 · Toy ECC encryption (secp256k1, small private key)

Assumption: Part 1 is an ElGamal/ECIES-style scheme. Curve y² = x³ + 7 over p = 2²⁵⁶ − 2³² − 977 with standard generator G, but the private key d is limited to a small range. The shared point's x-coordinate is expanded into a keystream (XOR).

Click "Generate key pair" to start.

Algorithm and role of the keys

  1. Key generation: pick secret d (private), publish Q = d·G (public). Recovering d from Q is the elliptic-curve discrete logarithm problem (ECDLP).
  2. Encrypt: pick a fresh random k, send C1 = k·G, compute shared secret S = k·Q, XOR the message with a keystream derived from S.x.
  3. Decrypt: the receiver computes d·C1 = d·k·G = k·Q = S and rebuilds the same keystream. Public key encrypts (via k), private key decrypts, and k is a one-time ephemeral key.

2 · Caesar cipher

Encrypt E(m) = (m + k) mod 26, decrypt D(c) = (c − k) mod 26. The key k is the only secret.

Discussion. Long texts converge to the true distribution, so success approaches 100% beyond about 40 letters. Very short texts (under about 10 letters) are ambiguous: several shifts yield plausible-looking text, and unusual text (rare letters, other languages, names) skews the statistics. Chi-squared uses only unigram counts; bigrams add context and help on short inputs; dictionary search needs no statistics but fails when the text has few common words. Since there are only 26 keys, a human can read all 26 candidates, so statistics only automate the choice.

5 · Attacking the toy ECC

The public key Q is known. With d < 2bits, the attacker simply computes G, 2G, 3G, … until it equals Q. Then d decrypts everything. Uses the key pair and ciphertext from section 1.

Generate a key pair and encrypt first.

Versus the Caesar attack

The Caesar attack needs statistics because the cipher leaks the language through the ciphertext: it can rank candidate keys by how plausible the plaintext is. Here the ciphertext looks random, so there is no signal to rank candidates; the attack only works because a candidate d can be verified exactly (dG = Q), with no statistics involved. Cost is a count of keys, not a property of the data.

Why it fails against a real configuration

With d ~ 2²⁵⁶, linear search needs about 2²⁵⁶ steps; the best generic algorithms (BSGS, Pollard's rho) still need about √n ≈ 2¹²⁸ group operations, which is infeasible in time and memory. The BSGS button above shows the square-root speedup: 16-bit keys need only about 2⁸ steps.

6 · Weaknesses: key space versus design

From the restricted key space

  • Brute force and BSGS/rho in about 2b/2 steps.
  • Any small-d table can be precomputed once for all users.
  • Key-recovery also breaks every past message encrypted to Q.

From the toy design itself

  • Keystream reuse: the stream is S.x repeated every 32 bytes, so long messages leak via XOR of repeated blocks (a Vigenère-like weakness).
  • No authentication: ciphertexts are malleable; flip a bit, flip the plaintext bit.
  • Weak randomness for k: a repeated or biased k gives repeated S and keystream, and leaks plaintext XORs.
  • No KDF: use of raw S.x rather than a hash. No point validation: invalid-curve attacks on C1 are possible.

Other attacks

  • Pollard's rho / kangaroo (best generic ECDLP, optimized for bounded intervals).
  • Known-plaintext: plaintext XOR ciphertext yields the keystream directly.
  • Side channels in double-and-add; fault attacks.
  • Quantum: Shor's algorithm breaks ECDLP at any size.
